Security

Last Reviewed: April 29, 2026

TL;DR

JT Power Tools has two systems with very different threat models. Tweaks are DOM-only — no JS execution, no data exfiltration, no synthetic clicks on JT buttons. The worst-case attack is UI-redress (relabeling a button to deceive a user), and we've added an explicit clickjacking guard against that. MCP talks to JobTread's API and can write or delete data, so it's gated by an admin-controlled three-tier permission model with a default of read-only on every new key.

Why this page exists

If you're an admin or IT lead deciding whether to allow JT Power Tools in your org, or a contractor wondering what an extension that modifies JobTread can actually do, this page lays out our threat model honestly. We'd rather you read this and decide it's acceptable than wonder.

Two systems, two threat models

The extension ships two largely independent capabilities, each with its own boundaries:

  • Tweaks — user- or admin-authored DOM and CSS modifications applied client-side inside app.jobtread.com. Closed verb allowlist, hard-blocked from running scripts or reaching the network.
  • MCP server — a Cloudflare Worker that brokers AI tool calls (Claude, ChatGPT, Cursor, etc.) to JobTread's Pave API. Three-tier permission model (read / write / delete), org-scoped grant keys, server-side enforcement.

The two systems do not share a process, a DOM, or an auth surface. A compromise in one does not propagate to the other.

Tweaks — what they can and cannot do

What a malicious tweak can do

  • UI redress (clickjacking) — relabel a visible button (e.g. "Approve" → "Cancel") so a user clicks expecting one outcome and triggers another. Mitigated: the engine now refuses setText on primary-action buttons whose current text matches a destructive or financial action word (Approve, Confirm, Delete, Pay, Submit, Send, Sign, etc.). The guard checks <button>, <input type="submit|button">, and role="button" elements at runtime before applying.
  • Hide elements — remove confirmation dialogs or warning banners. The local-disable hatch in the popup gives members a way to opt out of any org_required tweak per-device.
  • Visually disrupt the page — restyle aggressively, scramble row order. Disruptive but not destructive — page reload restores everything.
  • Push tweaks to org members (admin only) — admins with org_required scope can deliver tweaks to every member of their license. Members cannot edit or delete those tweaks but can locally disable them on their device, and the extension shows a one-time transparency banner the first time a new org_required tweak appears so members are never silently managed.

What a malicious tweak cannot do

  • Execute JavaScript. No eval, no expression(), no inline <script>, no javascript: URIs. The CSS sanitizer parses every stylesheet via an AST and hard-rejects all of these.
  • Inject HTML. All text content goes through textContent. There is no innerHTML, insertHTML, or insertElement verb, and the validator refuses any verb outside the closed allowlist.
  • Load external resources. The CSS sanitizer restricts url(...) to https:// or data:image/ only. @import is forbidden. There is no fetch / XHR verb. This blocks the classic exfil-via-background-image trick.
  • Exfiltrate data. Nothing in the verb set can take DOM contents and transmit them. Even if a tweak reads visible information from the page, there is no transport.
  • Click JT's own buttons synthetically. The onEvent verb only intercepts user interactions; it cannot dispatch them. A tweak cannot click "Delete" on the user's behalf.
  • Touch other tabs or origins. Content scripts are scoped to app.jobtread.com via host_permissions. Tweaks have no access to chrome.* APIs or to other tabs.

Blast radius. Tweaks act inside one user's browser and only on JobTread pages. They can modify what that user sees and clicks but cannot reach JobTread's servers, your data, or any other tab. A tweak's effects on a user's view do not propagate back to JobTread. Other users see vanilla JT until they install or accept the same tweak.

Defense-in-depth on tweaks

  • Closed verb allowlist. addClass, removeClass, setStyle, hide, show, setText, onEvent, moveBefore, moveAfter, sortChildren. Anything not on this list is rejected.
  • CSS sanitizer with AST parsing. Rejects dangerous at-rules (@import, @charset, @namespace), dangerous values (expression(...), behavior:, -moz-binding:, non-allowlist url()), and bare html / body / :root / * selectors. Auto-scopes every selector to .jt-tweak-{id} so a tweak's styles cannot bleed outside its own elements. Idempotent — re-running the sanitizer on already-scoped CSS does not double-scope it.
  • Selector blocklist. No tweak selector can include .jt-tools-, .jt-popup-, or .jt-tweak-edit- prefixes — keeps tweaks from targeting the extension's own UI.
  • Server-side re-validation and re-sanitization. Every tweak written to the server runs through both the DSL validator and the CSS sanitizer again, server-side. The server never trusts the extension's claim that content has already been validated.
  • Engine re-validates before applying. Even after the server returns a tweak, the engine validates again before applying — defense in depth in case storage was modified outside the editor.
  • Auto-disable on breakage. If a tweak's selectors stop matching after JT ships a UI change (consecutive zero-match applies after the tweak previously worked), the engine auto-disables it and surfaces a clear "Auto-disabled (UI moved)" chip in the popup with a Re-enable button. Prevents tweaks from sitting silently broken.
  • Audit trail. Every tweak version is preserved immutably in tweak_versions. AI-authored tweaks attribute back to the human admin who issued the AI grant key via issued_for_account_id.

MCP — permission tiers and what each tier can do

The MCP server is the more sensitive surface — it talks to JobTread's authoritative API on behalf of an AI client. Three-tier permission model, admin-controlled per AI grant key. Default for new keys: read.

Tier Can call Cannot call
read (default) Context bundles (jobs, schedule, financial, CRM, catalog, workflow, bills), search, knowledge lookup, list/get tweaks, ctx_* helpers Anything that creates, modifies, or deletes JT data
write Read tier + create/update jobs, tasks, budgets, contacts, comments, time entries, daily logs, dashboards, workflows, catalog items, files, tweaks. Send/post operations (notes, bills approval, sender allowlist). Destructive ops (delete*, remove*, revoke*, reject*, cancelRun)
delete Write tier + destructive operations on every entity (delete a job, delete budget items, delete a workflow, reject a bill, cancel a running workflow, delete files / plans, etc.) Nothing — full access within the org locked to the key

Two-layer enforcement

  • Tool-level gate. Every MCP tool declares a category in TOOL_PERMISSIONS. The wrapper checks the calling key's tier against the tool's category before dispatch.
  • Op-level gate. Tools like jt_job_write accept an op enum that includes both non-destructive ops (create, update) and destructive ops (delete, deleteArea). For these tools, the wrapper escalates the required tier to delete when args.op is in the destructive set.
  • Single source of truth. The same canCall(permission, toolName, op) helper gates both the MCP wrapper and the REST handler — they cannot drift.

Defense-in-depth on MCP

  • Org locking. A grant key is bound to a specific JobTread org. Calls against any other org are rejected at validation time.
  • Permission refresh on every request. All three auth paths (legacy Bearer license:grant, session token, OAuth) re-resolve the calling key's tier from the database on every MCP call. Portal-driven permission changes take effect on the user's next tool call — no disconnect / reconnect required.
  • Per-tool usage telemetry. Every tool call is logged with success / failure, error reason, and duration in mcp_usage_log. Permission denials are explicitly tracked.
  • Audit attribution. Each AI grant key records issued_for_account_id — the portal account that created it. Tweaks (and other artifacts authored by AI clients) attribute back to the human admin, not just "the license."
  • Rate limiting. Brute-force attempts against the auth endpoints are rate-limited per IP via Cloudflare KV with exponential backoff.
  • Server-side validation of ALL inputs. The Worker never trusts the AI client. Schema validation, parameter typing, and the same CSS / DSL sanitizers used in the extension run again server-side for tweak writes.

What the MCP server stores

Operationally, the MCP server stores: license keys, account credentials (password hashes, never plaintext), encrypted JobTread grant keys, AI grant keys, MCP usage telemetry (tool name, success/failure, duration), and tweak content. It does not store JobTread project data, financials, or client information — those flow through the Worker and back to the AI client without persistence. See Privacy Policy for the full data inventory.

What we ask admins to do

  • Use the least-privileged MCP tier that works. Default new keys to read. Promote to write only for AI workflows that genuinely need to author content. Promote to delete only for trusted automations or one-off cleanup tasks, and consider rotating the key back down afterward.
  • Review your org_required tweaks before pushing. Members will see a transparency banner the first time a new org_required tweak lands on their device, but you should still socialize what you're pushing and why.
  • Rotate AI grant keys when an admin leaves the team. The portal's AI Keys page lets you rotate or remove keys without losing the audit trail.
  • Audit AI activity. The portal exposes per-tool usage so you can see what each AI key has actually called.

Reporting a security issue

If you've found a vulnerability or have a security concern, please email support@jtpowertools.com with "Security Report" in the subject line. We aim to acknowledge reports within two business days. Please include:

  • A description of the issue and its potential impact
  • Steps to reproduce, ideally with a minimal proof of concept
  • The version of the extension or MCP server (the Worker version is in the X-MCP-Version response header)

We don't currently run a paid bug bounty, but we'll credit reporters publicly with permission and we will not pursue legal action against good-faith research.

Changelog of security-relevant changes

Major security changes are flagged in the main changelog under the Security heading. Recent highlights:

  • setText clickjacking guard — engine refuses to relabel primary-action buttons whose current text matches a destructive / financial action word.
  • CSS sanitizer is idempotent — already-scoped CSS no longer double-scopes on re-save, eliminating a silent-failure mode.
  • OAuth permission tier refresh on every request — admin-driven permission changes take effect on the user's next tool call across all auth paths.
  • Auto-disable on tweak breakage — the engine surfaces silent failures instead of letting broken tweaks sit unnoticed after a JT UI change.
  • One-time transparency banner — members see a banner the first time a new org_required tweak appears on their device.
