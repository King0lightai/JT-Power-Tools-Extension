```html
<a href="https://app.jtpowertools.com/dashboard.html" target="_blank" class="portal-link-item">

  <div class="portal-link-text">

<a href="https://app.jtpowertools.com/dashboard.html#mcp" target="_blank" class="portal-link-item">
```


**Risk:** Trivial. If `dashboard` (no `.html`) doesn't 200 on the host, we revert to `dashboard.html#team`. One quick `curl` check before shipping.

**Estimate:** 2-line edit, single commit. ~5 min.

### 2. Hover text invisibility on themed dropdowns / list items

**Symptom:** When the user hovers over a JT dropdown item (e.g. tab-menu, action-row dropdown), the background recolors to a themed accent but the text stays in the cascaded body color — making the hover state read as "dark text on dark accent" or "invisible text". Repro: the screenshot shows `Gantt` row in a list-mode dropdown with hovered text that reads as the same color as its hovered background.

**Affected markup pattern (from JT):**
```html
<div role="button" tabindex="0" class="block w-full relative cursor-pointer p-3 text-left whitespace-nowrap hover:text-white hover:bg-blue-500">
  ...
  Gantt
</div>
```

**Diagnosis:**

Tailwind utility behavior:
- `hover:text-white` → on hover, `color: #ffffff` (specificity 0,2,0)
- `hover:bg-blue-500` → on hover, `background-color: #3b82f6` (specificity 0,2,0)

Custom Theme's [rgb-theme.js](../../JT-Tools-Master/features/rgb-theme.js):
- Has rules like `.bg-blue-50 / .bg-blue-100 { background-color: ${p.primary.selection} !important; }` — but these are NOT scoped to `:hover`.
- Has NO rule overriding `.hover\:bg-blue-500:hover` directly.
- Has NO rule overriding `.hover\:text-white:hover`.

Confirmed via `grep -n "hover\\\\:bg-blue\\|hover\\\\:text-white" JT-Tools-Master/features/rgb-theme.js` → 0 matches.

Hypothesis on what's happening:
- Tailwind's `hover:text-white` rule fires correctly, setting `color: #ffffff`.
- Tailwind's `hover:bg-blue-500` rule also fires, setting `background-color: #3b82f6`.
- BUT — somewhere upstream, a themed rule with `!important` on the parent's color or on a more-specific selector is winning specificity, keeping the text in the cascaded user-text color rather than letting the `hover:text-white` apply.

This is the same defensive pattern as the v4.8.3 fix for `bg-gray-700/800` (where we explicitly forced `color: white !important` because JT's coupling of `bg-gray-700` + `text-white` could be fragile).

**Fix sketch** ([rgb-theme.js](../../JT-Tools-Master/features/rgb-theme.js) CSS template):

```css
/* v4.8.4 — defensive hover-state contrast for themed dropdown / menu items.
   Tailwind's hover:text-white loses to upstream themed color rules without
   !important. Force white text on every hover-bg-blue variant JT uses. */
.hover\\:bg-blue-500:hover,
.hover\\:bg-blue-600:hover,
.hover\\:bg-blue-700:hover {
  background-color: ${p.primary.base} !important;
  color: white !important;
}

.hover\\:bg-blue-100:hover,
.hover\\:bg-blue-200:hover {
  background-color: ${p.primary.selection} !important;
  color: ${p.text.primary} !important;
}

/* Hover text-white universal override — wins against any cascaded color rule. */
.hover\\:text-white:hover {
  color: white !important;
}
```

**Surface estimate:** Need to grep JT for ALL `hover\\:bg-{color}-{N}` variants in use to know the full list. Probably blue-100/200/500/600/700 covers it; might also need green/red/yellow if any dropdown uses those.

**Risk:** Same as v4.8.3 — `color: white !important` may regress an unusual case where a JT dropdown item has a non-white-text icon child on hover. Spot-check via screenshot.

**Estimate:** 1 file (rgb-theme.js), ~25 lines added. Quick smoke test in preview to confirm hover renders correctly across multiple presets. Single commit. ~30 min total including grep + smoke test.

### 3. Yellow edit-highlight cell looks bad in light themes

**Symptom:** When a row in the budget grid has been edited, JT marks the changed cell with `bg-yellow-100` (Tailwind light yellow). In default JT this renders as a subtle pale-yellow tint. Under Custom Theme, the cell instead renders as a dark olive (`#46442e`) — which works in dark themes but reads as "burnt / badly themed" in light themes (e.g. Field Day, Paper).

**Location:** [`JT-Tools-Master/features/rgb-theme.js`](../../JT-Tools-Master/features/rgb-theme.js) line 696.

**Current:**
```css
/* Don't interfere with JT's yellow updated-cell highlighting */
/* Use a muted yellow that works with themed text (same approach as dark mode) */
.bg-yellow-100 {
  background-color: #46442e !important;
}
```

The comment says "Don't interfere" but the override IS interfering — by hardcoding a dark olive that doesn't adapt to bgIsDark. The hardcoded `#46442e` was the same value the dark-mode CSS uses, presumably copied here under the assumption it's universally OK. It isn't.

**Fix options (pick one):**

**A. Remove the override entirely.** Let JT's default `bg-yellow-100` (Tailwind's pale yellow) survive. Lightweight, matches user expectation of "yellow means edited", correct in both light and dark themes (Tailwind's pale yellow reads against any background).

```css
/* v4.8.4 — let JT's default bg-yellow-100 ride. The previous hardcoded
   #46442e dark olive was a dark-mode-tuned value that read as
   "burnt-themed" in light themes. The default Tailwind yellow-100 is
   subtle enough that it doesn't clash with custom themes. */
/* (rule deleted) */
```

**B. Replace with a theme-aware value.** Use OKLCH to compute a yellow tint at the right lightness for bgIsDark:

```css
.bg-yellow-100 {
  background-color: ${p.alerts.yellow.bg} !important;
}
```

This is the same value used for `bg-yellow-50` (alert containers) — would harmonize the edit-highlight with other yellow surfaces. But makes "edited" indistinguishable from "warning" semantically.

**C. Keep an "edited" semantic but make it adapt to bgIsDark:**

```css
.bg-yellow-100 {
  background-color: ${p.meta.bgIsDark ? '#46442e' : 'oklch(95% 0.08 95)'} !important;
}
```

(Or use `palette.js` to derive a theme-aware "edited" tint as a new top-level token.)

**Recommendation: A (delete the override).** Simpler, semantic, lightest-touch. JT's pale yellow-100 already conveys "edited" universally; we should stop fighting it. If users want the edit-highlight harmonized with their theme later, that's a v4.9 enhancement that can introduce a `palette.editHighlight` token.

**Risk:** Low. Default `bg-yellow-100` is `#fef9c3` per Tailwind — light enough to read against any of our 10 presets' backgrounds.

**Estimate:** 4 lines deleted in rgb-theme.js, single commit, ~5 min.
